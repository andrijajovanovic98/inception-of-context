A bónuszmodul célja és szerepe

Mit adnak a bónuszötletek a működő 1-3. részhez

Fejlesztői élmény
1. Dinamikus életciklus Újraindexelés
  • Az 1. részben a ChromaDB induláskor indexel, a figyelő pedig követi az eseményeket.
  • Mi történik egy külső git ágváltáskor, vagy ha az indexnek tiszta lap kell?
  • A POST /reindex futás közben minden fájlt újradarabol és újra beágyaz, és kitisztítja a figyelő nélkül törölt fájlok darabjait.
2. Vizuális audit Vizuális diff
  • A 3. rész egész fájlokat ír, a fejlesztőnek viszont a pontos kódkülönbséget kell átnéznie.
  • A vizuális diff motor színezett, soronkénti unified diffet készít a webes felületnek.
  • Zöld (+) a hozzáadás, piros (-) a törlés.
3. Git commit (bekapcsolható) Git commit
  • Bekapcsolt Auto Git Commit mellett a zöld patch commitolódik: csak a patch fájljai, más stage-elt munka soha.
  • A helyi modell Conventional Commit üzenetet ír a szándékból és a patch összefoglalójából (élőben: feat(calculator.py): add square method with rounding).

Újraindexelés igény szerint: POST /reindex

A vektoradatbázis teljes újraépítése futás közben, folyamat- vagy konténer-újraindítás nélkül

Dinamikus életciklus
A lépések Végrehajtás
  • 1. A hashek elfelejtése: reset_state(), így egy fájl sem marad ki változatlanként.
  • 2. Újradarabolás és beágyazás: az index_all(force=True) bejárja a célt, és minden darabot beágyaz az all-MiniLM-L6-v2-vel.
  • 3. Egyeztetés: a lemezről eltűnt fájlok darabjai törlődnek, akkor is, ha a törlést egy figyelő sem látta.
  • 4. Frissítés és jelzés: a BM25 korpusz és a szimbólumleltár újraépül; egy REINDEX esemény megjelenik az élő hírfolyamban. A ?full=false helyette inkrementális szinkront futtat.
API példa Kérés / válasz
# a real call against demo_app (0.49 s) $ curl -X POST http://127.0.0.1:8000/reindex { "status": "success", "message": "On-demand full reindex completed successfully", "full": true, "indexed_files": 5, "total_files": 4, "total_chunks": 23, "file_breakdown": {"calculator.py": 8, "formatter.py": 7, "main.py": 5, "ioc.config.yml": 3} } # indexed_files counts the empty __init__.py too
Bónusz

Vizuális diff motor: bonus/diff_engine.py

Strukturált, ember által ellenőrizhető kódkülönbség a böngészőben

Diff motor
Hogyan készül a diff Architektúra
  • A Python beépített difflib.unified_diff algoritmusára épül.
  • A sorokat hozzáadásra (+), törlésre (-) és változatlan környezetre bontja.
  • Megszámolja a változott sorokat: a square metódus patchje +4 / -0.
  • A diff a futás előtti eredetikhez képest készül, így egy már alkalmazott (zöld) patch diffje is látszik.
A diff megjelenítése UI nézet
--- a/calculator.py +++ b/calculator.py @@ -34,3 +34,7 @@ def power(self, base: float, exp: float) -> float: """Return base raised to the power of exp.""" return round(base ** exp, self.precision) + + def square(self, a: float) -> float: + """Return the square of a number rounded to precision.""" + return round(a * a, self.precision)

Automatikus Git commit: bonus/git_committer.py

Ellenőrzött módosítások commitolása a helyi LLM által írt Conventional Commit üzenettel

Git automatizálás
A commitüzenet promptja LLM generálás

A helyi modell megkapja a szándékot, a patch összefoglalóját és az érintett fájlok nevét (diffet nem), és egy sort ad vissza:

Generate a single concise Conventional Commit message following the format: <type>(<scope>): <short description> Allowed types: feat, fix, refactor, test, docs, chore. Rules: - Exactly ONE line only. - Do not use quotes or markdown formatting. - Be brief and descriptive (max 72 characters). Coding Intent: {intent} Patch Explanation: {patch summary} Touched Files: {file names} Commit message:
Biztonságos git műveletek Alfolyamat
  • Csak siker után, bekapcsolva: kizárólag zöld validáció után, és csak bekapcsolt Auto Git Commit mellett.
  • Pontos stage-elés: git add -A -- <paths>, majd git commit -- <paths>: más stage-elt munka kimarad a commitból.
  • A hash és az üzenet visszakerül a dashboardra; a sikertelen commit látszik, soha nem csendes. Ha az Ollama nem fut, sablonüzenet készül.

Dry-run mód: kockázatmentes előnézet

Teljes patch-generálás, diffszámítás és sanity ellenőrzés a lemez módosítása nélkül

Biztonsági mód
Miért hasznos a dry-run Haszon
  • A fejlesztő és az értékelő megnézheti, mit csinálna a modell, mielőtt bármi a lemezre kerülne.
  • Egy generálás, validáció nélkül: gyors pillantás arra, mit változtatna a modell.
  • A Patch Loop & Bonus fül Dry-Run Mode jelölőnégyzetével, vagy a CLI --dry-run kapcsolójával.
Hogyan kezeli a motor Végrehajtás
  • A modell elkészíti a strukturált JSON patchet.
  • A 6 sanity ellenőrzés és az őrök átvizsgálják a memóriában lévő kódot.
  • A diff motor kiszámolja a unified diffet a jelenlegi fájlokhoz képest.
  • A futás biztonságosan megáll: nincs lemezírás, nincs ideiglenes fájl, nincs tesztfolyamat.

B3: Docker SDK összeomlás-figyelő

Egy célszolgáltatás naplójának figyelése, összeomláskor patch-ciklus

bonus/crash_watcher.py
Docker SDK integráció bonus/crash_watcher.py
  • A CrashWatcher egy konténer naplófolyamát követi a Docker SDK-n át (docker.from_env()).
  • A napló vége 200 soros gyűrűs pufferben, élőben látszik a dashboardon.
  • Nem nulla kilépési kód = összeomlás; mindegyiket egyszer kezeli (kulcs: FinishedAt).
Összeomlás → patch-ciklus Önjavítás
  • A napló vége lesz a patch szándéka; a stack frame-ek a célhoz relatív file:line in function alakra íródnak át.
  • Ugyanazt a patch-ciklust, zárat és előzményt használja, mint a Patch Loop fül.
  • Zöld patch → a szolgáltatás újraindul; piros patch → leállítva marad egy embernek.
  • Az egymást követő összeomlás-futások száma korlátos (3), így egy hibás szolgáltatás nem foglalhatja le a modellt.
Végpontok és Makefile Futtatás
  • API: POST /bonus/crash-watch (indítás), GET (állapot), DELETE (leállítás).
  • A make demo-service a célt összeomolható szolgáltatáskonténerként futtatja.
  • A make bonus WATCH_CONTAINER=ioc-demo-service elindítja a figyelőt.
  • Crash Watcher kártya a bonus/dashboard.py-ban, élő naplóval és összeomlás-előzménnyel.
