Hybrid Retrieval: Dense Vectors & Sparse BM25Okapi

Why vector similarity alone fails on source code queries and how hybrid search fixes it

Search Engine
Dense Search (ChromaDB + all-MiniLM) Semantics
  • How It Works: Maps text into 384-dimensional vector space; computes cosine distance.
  • Strengths: Understands user intent and synonyms (e.g. "addition function" -> finds add).
  • Weakness in Code: Vulnerable to false positives on exact identifier names, method names, and acronyms.
results = collection.query( query_texts=[query], n_results=top_k * 2 )
Sparse Search (BM25Okapi) Exact Keywords
  • How It Works: TF-IDF variant measuring exact term frequency and inverse document frequency.
  • Strengths: Flawlessly matches exact identifiers like format_result or CalculatorError.
  • Weakness: Incapable of semantic understanding when terms do not explicitly overlap.
tokenized_query = query.lower().split() bm25_scores = bm25.get_scores(tokenized_query)

Symbol Pre-Resolution: Eliminating Hallucinations

Guaranteeing 100% factual accuracy for code symbol existence questions

Anti-Hallucination
The Challenge: LLM Symbol Hallucination Risk
  • Subject Mandate: "The /ask system must avoid hallucinating code symbols. Questions such as 'is there a function called X?' must be answered based on known indexed information."
  • If a 3B model is simply prompted "Is there a power() function?", it may plausibly guess "Yes, in calculator.py" even when it does not exist!
  • Purely generative token predictors favor probability over ground-truth negatives.
The IoC Solution: Deterministic Pre-Resolution Engine Solution
  • 1. Pattern Interception: Detect symbol inquiries using regex patterns (e.g. is there a function called X?).
  • 2. AST Symbol Table: Query the indexed symbol table extracted during AST chunking (functions, classes, methods).
  • 3. Fact Injection: If a user asks for power and it does not exist, inject an explicit factual negative constraint: "The requested symbol DOES NOT exist in the codebase."
Defense Tip: This two-layer safeguard guarantees that the 3B model never hallucinates non-existent functions during evaluation!

Reciprocal Rank Fusion (RRF) Algorithm

Mathematically merging disparate score distributions into an optimal ranking

Algorithm
The Fusion Formula Mathematics

Cosine similarities (0 to 1) and BM25 scores (unbounded positive reals) cannot be directly added without calibration. RRF normalizes across ranks:

RRF_Score(d) = SUM [ 1 / ( k + rank_i(d) ) ] k = 60 (standard smoothing constant)
  • Chunks ranking near the top in both systems receive the highest cumulative RRF score.
  • Documents appearing in only one list are appropriately smoothed, preventing outlier skew.
Implementation: p2/retriever.py Code
def hybrid_retrieve(query: str, top_k: int = 4): dense_hits = chroma_client.query(query, n=top_k*2) sparse_scores = bm25.get_scores(query.split()) rrf_scores = {} for rank, doc_id in enumerate(dense_hits): rrf_scores[doc_id] = rrf_scores.get(doc_id, 0) + 1.0 / (60 + rank) for rank, (doc_id, _) in enumerate(sorted_bm25): rrf_scores[doc_id] = rrf_scores.get(doc_id, 0) + 1.0 / (60 + rank) return sorted(rrf_scores.items(), key=lambda x: x[1], reverse=True)[:top_k]

Summary & Defense Guidelines

Core talking points for peer evaluators during the Part 2 defense

Defense Ready
1. Why Hybrid Search? Retrieval
  • Answer: Dense cosine search struggles on exact identifiers and short variable names, while BM25 lacks semantic intuition.
  • Combining both via Reciprocal Rank Fusion guarantees both semantic understanding and identifier precision.
2. How Anti-Hallucination Works? Safety
  • Answer: Deterministic AST symbol pre-resolution.
  • When the user asks whether a function exists, the system verifies against indexed AST symbols and injects ground truth before model inference.
3. Prove It Is 100% Local! Offline
  • Answer: Disconnect network access or inspect Docker network routing.
  • Ollama evaluates strictly on 127.0.0.1:11435. Zero external cloud requests occur.
