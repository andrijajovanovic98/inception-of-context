INCEPTION OF CONTEXT - PART 3

Patch Generation & Self-Healing Loop

Structured JSON, 6 Hard Refusals, Atomic Staging, and Verified Rollback

In Part 3, IoC evolves into an autonomous coding agent. Driven by user intent, it gathers project context, produces structured file modifications, refuses unsafe patches before any disk write, runs the project's validation command, and feeds every failure back to the model for up to 3 attempts - or rolls back to the exact pre-run bytes.

Part 3 Specification: This is a LOOP

What does the official subject mandate for the third phase?

Subject Audit
Not Merely Separate Endpoints The Loop
  • Core Subject Sentence: "The deliverable is a loop, not a list of endpoints."
  • One intent (the subject's examples: "add a healthcheck route", "rename foo to bar") drives the whole flow.
  • The system independently drives forward until verified success or safe restoration.
Strict Pre-Flight Validation Sanity Checks
  • Zero Blind Disk Writes: Raw LLM generated patches must never directly overwrite source files.
  • 6 Mandatory Refusals: Stub functions, severe shrinkage, leaking retrieval prompt headers, etc.
  • Hard refusals, not warnings: checked before any disk write.
Validation & Rollback Guarantee Safety First
  • ioc.config.yml: External configuration specifies compilation and testing routines.
  • 3 Attempts: the error log goes back to the model for another attempt.
  • Exact Rollback: after three attempts without a green validation, back to the exact pre-run state.

The Autonomous Patch Loop Step by Step

How execution flows from high-level intent to atomic repository updates

Control Flow
Step 1 Intent & Retrieval p3/loop.py Top-k chunks from the hybrid retriever; the files the intent names are shown in full (and their callers for a rename).
->
Step 2 Structured JSON Patch qwen2.5:3b Generate complete post-change file contents in structured JSON rather than brittle diffs.
->
Step 3 6 Sanity Checks p3/sanity.py Six hard refusals plus guards; any failure refuses the patch before disk and goes back to the model.
Step 4 Snapshots & *.ioc.tmp p3/applier.py Capture baseline snapshots. Stage writes to temporary files before atomic swap.
->

->

Why Structured JSON and NOT Free-Form Diffs?

Addressing small language model limitations through deterministic representation

JSON Schema
Failure of Free-Form Diffs Problematic
  • Small 3B models frequently miscalculate hunk header line counts: @@ -14,6 +14,8 @@.
  • A single misplaced whitespace or indentation tab causes patch or git apply to fail.
  • Subject rule: "The patch is structured JSON, not free-form text and never a diff."
The Reference Shape (Subject VI.3) JSON Schema
{ "summary": "Add a square method to Calculator", "files": [ { "path": "calculator.py", "op": "modify", "content": "<every line of calculator.py, plus square()>" } ] }

op: create, modify or delete; content: the complete post-change file, quotes and backslashes masked as @@DQ@@, @@BS@@.

Part 3

The 6 Mandatory Sanity Checks (Immediate Refusal)

Hard refusals in p3/sanity.py, run before any disk write; the reason goes back to the model

Hard Refusals
# Sanity Check Why It Fails (Subject Rationale) Detection Technique
1 Retrieval marker leakage Model echoes prompt headers like === RELEVANT CODEBASE CONTEXT === or --- File: into code. Substring check against every marker in p1/markers.py, the constants both prompts are built from.
2 Creating existing file Using create on a file that already exists on disk risks silent overwrite. Filesystem check: os.path.isfile(path).
3 Empty or null replacement Replacing non-empty code with "", "None", or "null" causes file loss. Stripped content compared with "", None, null; an empty create is refused too.
4 Stub-only functions Lazy placeholder bodies: pass, ..., return None, raise NotImplementedError, or a constant return marked as a placeholder. AST: a new function whose body (docstring aside) is only one of those; comments are read for the placeholder mark.
5 File shrinkage (> 60%) Drastic unexpected size reduction signals code loss or truncated output. Check: len(new) < len(old) * 0.4.
6 More than 3 files modified Preventing runaway hallucinations: 1 patch is limited to at most 3 source files. Check: len(patch["files"]) > 3.

Also refused: invalid Python (the syntax gate), any edit of ioc.config.yml, a patch that changes nothing, paths outside the target or into hidden or vendored files, removing a definition, an error check or the __main__ block the intent does not name, code that never runs (behind a condition that never holds, after a return, a raise its own except swallows), and a rename that puts the new name where the old one never was.

Atomic Staging and Snapshotting

Guaranteeing filesystem integrity against crashes and partial write failures

Atomic Safety
Step 1: In-Memory Baseline Snapshot Snapshot
  • Before any write, each touched file's raw bytes and mode (and, under root, its owner) are kept, keyed by its canonical path: ./calc.py and calc.py are one entry.
  • For a newly created file, rollback deletes it, and the directories the run created with it.
with open(full_path, "rb") as f: content = f.read() # bytes: CRLF and odd bytes survive st = os.stat(full_path) mode = stat.S_IMODE(st.st_mode) # +x survives too
Step 2: *.ioc.tmp Staging & os.replace Atomicity
  • Generated content is first written to temporary sibling files, calculator.py.ioc.tmp, each one fsync'ed.
  • Only after all files stage successfully does the system execute POSIX atomic swaps: os.replace(tmp_path, target_path).
  • A failure while staging removes the temporaries and restores the snapshot: nothing half-written is ever renamed into place.

Validation Engine & ioc.config.yml

Decoupling project-specific build and test routines from the IoC core engine

Config Driven
Configuration: demo_app/ioc.config.yml YAML Spec
validation_command: "python3 -m py_compile {files} && python3 -m flake8 --select=E9,F63,F7,F82 {files} && python3 main.py" # one line in the file validation_file_extensions: [".py"]
  • {files}: the touched files with a listed extension; a patch touching none (a README) validates every .py file instead.
  • Three gates: it compiles, no undefined names (flake8 E9/F63/F7/F82), it runs.
Execution: p3/loop.py Subprocess
  • Read once, before the first attempt: a patch cannot rewrite its own judge (and may not touch ioc.config.yml).
  • subprocess.Popen in its own session, on a worker thread; after 30 s the whole process group is killed.
  • No __pycache__ in the target (PYTHONDONTWRITEBYTECODE, PYTHONPYCACHEPREFIX); the target's own modules are imported first.
  • Exit code and output (the last 2000 characters) go back to the model.

Self-Healing Retry Loop: Autonomous Error Feedback

Every refusal or red validation goes back to the model verbatim; the files are restored in between

Retry Engine
Attempt 1 Fails Validation Failure

A red attempt, replayed by make test with a scripted model: the patch left an undefined name in main.py.

CRITICAL: You MUST correct these specific errors in this attempt. Do not repeat the same mistake. Output the corrected, complete JSON patch.

100% Rollback Guarantee: Zero Code Corruption

A non-negotiable peer evaluation requirement: the repository must never be left in a broken state

Fail-Safe
When Does Rollback Trigger? Triggers
  • All 3 attempts end red (refused, unparseable or failed validation); after each red attempt the files are restored first.
  • A failure while staging the files.
  • The run is cancelled (Ctrl+C, server shutdown).
How Does Rollback Execute? Mechanism
  • Snapshotted bytes and mode are written back through *.ioc.tmp and os.replace.
  • Created files (op: create) are deleted, with the directories they brought.
  • Leftover *.ioc.tmp files are removed, then every file is compared byte for byte with its snapshot: rollback_verified.
Peer Evaluation Proof Audit
  • Running git status and git diff demonstrates an entirely clean working tree.
  • The CLI prints Rollback verified: every touched file matches its pre-call snapshot byte-for-byte.
