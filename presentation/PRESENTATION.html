Chunking Engine

Logical Code Chunking: AST vs. Fixed Size

Why character slicing destroys code context and how AST preserves syntax

chunker.py
Fixed-Size Chunking (Rejected) Naive 500 Chars
  • Cuts Functions Arbitrarily: Blind character boundaries split function headers from their bodies or return statements.
  • Destroys Syntax: Emits incomplete code fragments with unmatched parentheses and dangling indentation.
  • Loses Parameter Signatures: The AI retriever might fetch only lines 10-15 without knowing what arguments the function takes.
  • Subject Violation: Chapter VI.1 explicitly states that fixed-size chunking fails this part.
ASTChunker in IoC (Implemented) Python AST
  • Tree Parsing: Uses Python's built-in ast.parse() to discover exact syntactic nodes: functions, classes, and methods.
  • Decorator Safety: _get_start_line_with_decorators() groups @staticmethod or decorators with their function.
  • Symbol Hierarchy: Detects classes and treats each method as a separate, self-contained chunk (e.g. Calculator.add).
  • Exact Line Ranges: Attaches 1-indexed start_line and end_line for pinpoint line accuracy.
  • Fallbacks: RegexPythonChunker (def/class headers at any indentation) for Python that does not parse; FallbackChunker (blank-line blocks) for other files.

Every record links its chunk ID (file:symbol:first line) to its source text, its metadata (file_path, symbol_name, symbol_type, start_line, end_line, content_hash) and its 384-d vector.
HNSW Vector Graph Index Sub-millisecond
  • Hierarchical Navigable Small World (HNSW): Multi-layer graph connecting high-dimensional vector nodes.
  • Cosine Distance (hnsw:space: "cosine"): Measures angular divergence (\(1 - \cos(\theta)\)):
    • Angle ≈ 0° → Identical / closely related meaning
    • Angle ≈ 90° → Unrelated code semantics
  • Logarithmic Traversal: HNSW hops across high-layer expressways in \(O(\log N)\) time instead of scanning all records.
  • Local Filesystem: persisted in --db-dir (default .chroma_db/; make uses /tmp/ioc/chroma_db). 100% offline.
Indexing Engine

How Indexing Works: From File to Vector

The 4-stage lifecycle of a source file during the indexing process

indexer.py • db.py
1. Read & Filter Step 01
  • Indexer encounters calculator.py.
  • should_ignore_path() checks ignore rules (skips .git, venv, .chroma_db).
  • is_binary_file() sniffs the first 1024 bytes; a \x00 anywhere in the text also makes the file binary.
2. Hash Check Step 02
  • Computes compute_sha256(content) on disk.
  • Compares against stored hash in index_state.json.
  • If Match: Bypassed immediately (0ms).
  • If Different: Continues to Step 3.
3. Embed Chunks Step 03
  • Splits source into CodeChunk objects via AST.
  • Each chunk's text is passed to all-MiniLM-L6-v2.
  • Outputs a 384-dimensional dense vector encoding the code semantics.
4. DB Upsert Step 04
  • Per chunk: vanished ids deleted, new or changed chunks re-embedded, unchanged ones kept.
  • Inserts document text, embeddings & line metadata.
  • Saves new SHA-256 hash in index_state.json.
Change Detection

Incremental Synchronization: 3 Simple Scenarios

Concrete examples of how the indexer handles unchanged, modified, and deleted files

indexer.py
Case A: Unchanged File Fast Skip
  • Disk hash == index_state.json hash.
  • Action: Skipped immediately.
  • Cost: 0 embeddings, 0 DB writes, ~0.1ms compute.
  • Example: formatter.py hasn't been edited → bypassed completely.
Case B: Modified File Upsert
  • Disk hash ≠ index_state.json hash.
  • Step 1: re-chunk the file; compare each chunk's hash, lines and name with what ChromaDB holds.
  • Step 2: upsert_chunks() only for changed chunks: live, "1 chunk(s) re-embedded, 7 unchanged".
  • Step 3: Updates new hash in state file.
Case C: Deleted File Purge
  • File was tracked but now absent from disk.
  • Action: delete_file_chunks(path) purges all its chunk IDs; every scan also reconciles with what ChromaDB holds.
  • Purges key from index_state.json.
  • Result: Zero dead vectors or phantom symbols.
Pipeline: Read File → Compute SHA-256 → Compare Hash State → ✓ Atomic ChromaDB Update
Filesystem Watcher

Watch Mode & Real-Time Synchronization

Debounced event handling with a dedicated Docker polling fallback

watcher.py
Event Handling & Debounce Engine Watchdog
  • Handler: CodebaseChangeHandler catches on_modified, on_created, on_deleted, and on_moved.
  • Debounce Window (0.5s): Coalesces rapid sequential disk writes (e.g. editor temp files and auto-save bursts) to prevent indexing churn.
  • Worker Loop: _process_pending_loop runs on a background daemon thread, processing ready events sequentially.
Polling Fallback Loop (Subject Requirement) Overlayfs Safe
  • Why it exists: On container filesystems (Docker bind mounts, btrfs, overlayfs), inotify can silently drop file events.
  • Implementation: _polling_fallback_loop executes every 10 seconds in the background.
  • Mechanism: Triggers an incremental indexer.index_all() scan, guaranteeing eventual consistency if inotify drops an event.
  • Activity Buffer: Ring buffer (max 100 logs) feeds SSE live broadcasts.
Safety Rules

Exclusions & Self-Referential Loop Defense

Preventing index contamination, infinite watcher feedback, and binary bloat

Subject Rule VI.1
Ignored Directories Filtered
  • .git (VCS internal data)
  • node_modules (Vendor libraries)
  • dist, build (Artifacts)
  • venv, .venv, env, .env
  • __pycache__, .pytest_cache
  • Hidden directories (starting with .)
Vector DB Loop Prevention Critical Rule
  • The Danger: If the vector database folder is watched, ChromaDB writes trigger the watcher, causing an infinite indexing loop!
  • The Defense: should_ignore_path() excludes .chroma and .chroma_db by name; CodebaseIndexer.is_ignored() also excludes the configured store by its real location.
Binary File Protection Content Check
  • Extension filter: .pyc, .so, .dll, .exe, .png, .jpg, .pdf, .zip, .safetensors, .gguf.
  • Null-byte detection: is_binary_file() sniffs the first 1024 bytes, and a \x00 anywhere in the text marks the file binary too.

Hybrid Retrieval: Dense Vectors & Sparse BM25Okapi

Why vector similarity alone fails on source code queries and how hybrid search fixes it

Search Engine
Dense Search (ChromaDB + all-MiniLM) Semantics
  • How It Works: Maps text into 384-dimensional vector space; computes cosine distance.
  • Strengths: paraphrased intent: "how is a value formatted as currency?" ranks format_currency first (0.88).
  • Weakness in Code: weaker on exact identifier matches: "where is X used?" can miss the caller entirely (subject VI.2).
candidate_count = max(target_k * 3, min(total_count, 15)) chroma_res = self.db.query(query_text=query, n_results=candidate_count) dense = max(0.0, min(1.0, 1.0 - float(dist)))
Sparse Search (BM25Okapi) Exact Keywords
  • How It Works: TF-IDF variant measuring exact term frequency and inverse document frequency.
  • Strengths: exact identifiers: "where is multiply used?" also ranks the caller calculate_tax in main.py.
  • Weakness: no semantics: a light stemmer folds inflections ("divides" meets divide), but a synonym never matches.
query_tokens = tokenize_code(query) # format_currency -> # format_currency, format, currency # divides -> divid, like divide raw_bm25 = bm25.get_scores(query_tokens) bm25 = score / max(raw_bm25) # scaled to [0, 1]
Part 2

Symbol Pre-Resolution: Truthful Answers

The two question shapes the subject grades are answered from the index, not by the model

Anti-Hallucination
The Challenge: LLM Symbol Hallucination Risk
  • Subject (VI.2): "is there a function called X?" and "what functions exist in this file?" are easy for a small model to get wrong; on those, /ask must not hallucinate symbols that are not in the index.
  • Measured before the fix: asked for the functions of main.py, the 3B model answered <entrypoint>, the indexer's name for the __main__ block.
  • Purely generative token predictors favor probability over ground-truth negatives.
The IoC Solution: Deterministic Pre-Resolution Engine Solution
  • 1. Question Shapes: resolve_symbol_query() recognises both shapes in their natural variants: backticks, Class.method, "does X exist", "which functions are in <file>", Hungarian.
  • 2. Symbol Inventory: functions, methods and classes of the indexed AST chunks with their line ranges; module blocks are not symbols.
  • 3. The Index Answers: a question that is only that fact never reaches the model (answer_source: "index"); for broader questions the verified fact leads and names found nowhere in the code are flagged.
Defense Tip: ask "is there a function called sqrt?": the badge reads "Answered from the index (model not consulted)".
Part 2

Hybrid Score Fusion: Dense + BM25

How p2/retriever.py turns two score scales into one similarity score per chunk

Algorithm
The Fusion Formula Mathematics

Cosine similarity is already in [0, 1]; BM25 is unbounded, so it is first divided by the best BM25 score of the query. Then a weighted sum:

score = 0.5 × dense + 0.5 × bm25 / max(bm25) + 0.25 if the query names the symbol + 0.15 if the query names the file score = min(score, 1.0)
  • Candidates: the dense hits plus the best BM25 hits, max(3 × k, 15) of each on the demo index.
  • Equal scores are ordered by file and line, so a query always ranks the same way.
  • ChromaDB stays the canonical store: the BM25 corpus is rebuilt from its documents after every index change.
Implementation: p2/retriever.py Code
# Retriever.retrieve(query, k=3, alpha=0.5), abridged combined_score = (alpha * d_score) + ((1.0 - alpha) * b_score) boost = 0.0 if symbol_name and (symbol_name in query_words or short_sym in query_words): boost += 0.25 if file_stem and file_stem in query_words: boost += 0.15 final_score = min(1.0, combined_score + boost) # ties break on location: a stable ranking scored_candidates.sort(key=lambda x: (-x[0], str(x[1]["file_path"]), int(x[1]["start_line"] or 0)))

Part 3

The 6 Mandatory Sanity Checks (Immediate Refusal)

Hard refusals in p3/sanity.py, run before any disk write; the reason goes back to the model

Hard Refusals
# Sanity Check Why It Fails (Subject Rationale) Detection Technique
1 Retrieval marker leakage Model echoes prompt headers like === RELEVANT CODEBASE CONTEXT === or --- File: into code. Substring check against every marker in p1/markers.py, the constants both prompts are built from.
2 Creating existing file Using create on a file that already exists on disk risks silent overwrite. Filesystem check: os.path.isfile(path).
3 Empty or null replacement Replacing non-empty code with "", "None", or "null" causes file loss. Stripped content compared with "", None, null; an empty create is refused too.
4 Stub-only functions Lazy placeholder bodies: pass, ..., return None, raise NotImplementedError, or a constant return marked as a placeholder. AST: a new function whose body (docstring aside) is only one of those; comments are read for the placeholder mark.
5 File shrinkage (> 60%) Drastic unexpected size reduction signals code loss or truncated output. Check: len(new) < len(old) * 0.4.
6 More than 3 files modified Preventing runaway hallucinations: 1 patch is limited to at most 3 source files. Check: len(patch["files"]) > 3.

Also refused: invalid Python (the syntax gate), any edit of ioc.config.yml, a patch that changes nothing, paths outside the target or into hidden or vendored files, removing a definition, an error check or the __main__ block the intent does not name, code that never runs (behind a condition that never holds, after a return, a raise its own except swallows), and a rename that puts the new name where the old one never was.

Atomic Staging and Snapshotting

Guaranteeing filesystem integrity against crashes and partial write failures

Atomic Safety
Step 1: In-Memory Baseline Snapshot Snapshot
  • Before any write, each touched file's raw bytes and mode (and, under root, its owner) are kept, keyed by its canonical path: ./calc.py and calc.py are one entry.
  • For a newly created file, rollback deletes it, and the directories the run created with it.
with open(full_path, "rb") as f: content = f.read() # bytes: CRLF and odd bytes survive st = os.stat(full_path) mode = stat.S_IMODE(st.st_mode) # +x survives too
Step 2: *.ioc.tmp Staging & os.replace Atomicity
  • Generated content is first written to temporary sibling files, calculator.py.ioc.tmp, each one fsync'ed.
  • Only after all files stage successfully does the system execute POSIX atomic swaps: os.replace(tmp_path, target_path).
  • A failure while staging removes the temporaries and restores the snapshot: nothing half-written is ever renamed into place.

A non-negotiable peer evaluation requirement: the repository must never be left in a broken state

Fail-Safe

B3: Docker SDK Crash Watcher

Watch a target service's logs and trigger the patch loop on crash

bonus/crash_watcher.py
Docker SDK Integration bonus/crash_watcher.py
  • CrashWatcher follows one container's log stream via the Docker SDK (docker.from_env()).
  • Log tail kept in a 200-line ring buffer, shown live on the dashboard.
  • Non-zero exit code = crash; each crash handled once (keyed by FinishedAt).
Crash → Patch Loop Self-Healing
  • Log tail becomes the patch intent; stack frames rewritten to target-relative file:line in function.
  • Runs the same patch loop, lock and history as the Patch Loop tab.
  • Green patch → service restarted; red patch → left stopped for a human.
  • Consecutive crash runs capped (3) so a broken service cannot keep the model busy.
Endpoints & Makefile Run It
  • API: POST /bonus/crash-watch (start), GET (status), DELETE (stop).
